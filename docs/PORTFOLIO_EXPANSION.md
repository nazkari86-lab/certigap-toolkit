# AutoIndex Portfolio Expansion

The portfolio should grow by capability, not by algorithm name. A candidate is
admissible only when it:

1. implements the same declared operations and aggregate semantics;
2. has executable Python and generated C++ runtimes;
3. exposes deterministic memory, build, and per-operation cost accounting;
4. is regenerated by the independent verifier;
5. passes randomized oracle and tamper tests;
6. has at least one non-calibrated workload or constraint region where it is
   not dominated by every existing candidate.

This policy prevents a large but misleading leaderboard.

## Current Grammar

The v2 grammar supports fixed rank-addressed arrays, point updates, point gets,
and contiguous `sum`, `min`, or `max` queries. Its eight candidates cover:

| Candidate | Best-fit region | Main limitation |
|---|---|---|
| sorted array | points, updates, very tight memory | linear ranges |
| prefix sum | static or read-heavy sums | linear update suffix |
| Fenwick | mixed sum ranges and updates | sum only |
| sqrt decomposition | sublinear ranges under tight memory | square-root work |
| segment tree | general dynamic aggregates | roughly `2*pow2(n)` slots |
| sparse table | nearly static `min`/`max` | rebuild after updates |
| CertiRange point | skewed point routing, snapshots | larger state |
| CertiRange range | skewed mixed routing, snapshots | heuristic topology search |

## Honest Next Candidates

Candidates that preserve the current operation grammar can be evaluated next:

- disjoint sparse table for static associative sums with constant-time ranges;
- cache-aware blocked Fenwick for large arrays;
- arity-tuned segment trees for cache-line and SIMD tradeoffs;
- persistent segment tree as a conventional snapshot baseline;
- succinct static RMQ for memory-constrained immutable `min`/`max`;
- synthesized two-level prefix layouts from CertiGap-H, after their hardware
  cost units are reconciled with AutoIndex units.

These should not be merged until native calibration demonstrates a distinct
win region. Multiple block sizes or arities are parameters of one family, not
new algorithm claims.

## Capability Extensions

The following structures need new query grammars and separate leaderboards:

- lazy segment tree and dual Fenwick for range updates;
- wavelet tree and merge-sort tree for rank, count, and kth queries;
- treap, AVL, B-tree, and learned indexes for dynamic or non-dense keys;
- LSM and page-oriented B-trees for disk and storage-engine objectives;
- multidimensional Fenwick, range tree, and kd-tree for spatial keys.

A future artifact should declare required capabilities first, filter to the
matching grammar, and only then optimize cost. Comparing these structures on
the current three-operation trace would be scientifically invalid.

## Measurement Gate

Structural work remains a replayable proxy, not latency. Before production
selection, every backend needs target-specific medians for get, range, update,
build, and migration, plus memory bytes and p95/p99 observations. Selection
should fail closed to a safe baseline when confidence intervals overlap or the
holdout trace shows material regression.
